# Native Windows worker (CPU, trusted account)

`windows_worker.py` implements a Windows-local JSON worker lifecycle. For authenticated remote execution, use the separate `windows_remote_tools.py` client and [Windows SSH guide](windows-remote-execution.md). Native worker acceptance and SSH transport acceptance are separate checks; hosted acceptance applies to the tested source and runner. The existing `remote_tools.py` client retains its POSIX protocol.

Deploy the source on an explicitly selected Windows account with a dedicated job root protected by that account's ACLs. The worker does not configure or verify ACL isolation. Commands execute with the account's ambient privileges and environment; wall/output/log controls are cooperative polling limits, not a security sandbox, memory limit or network policy. Only bounded CPU manifests are accepted. No credentials belong in profiles, manifests or staged inputs. Approving a profile does not authorize execution or data transfer.

## JSON subprocess protocol

Invoke `python windows_worker.py` with one UTF-8 JSON request on stdin; one JSON reply is written on stdout. The request has `protocol: 1`, `operation`, `remote_root` (native absolute dedicated path), `expected_hostname`, `expected_user`, `job_id` and `manifest_sha256`. `inspect` may omit job identity and pins; it returns the observed host/user to pin before any job operation. Job operations require exact pins. Use existing v1 trusted-job manifest fields (`schema_version`, `job_id`, `argv`, `inputs`, `outputs`, `resources`, `required_device: "cpu"`) and SHA-256 of its canonical sorted compact UTF-8 JSON. Job IDs are 32 lowercase hex digits. Resource bounds match the original CPU worker: wall time 1–3600 seconds, threads 1–16, output at most 16 MiB, logs at most 1 MiB each, explicit declared outputs.

`prepare` additionally requires `manifest`, `files` and `worker_source` containing the exact reviewed `windows_worker.py` source. Each transferred file is `{path,sha256,data}` with base64 data and a matching declared input destination/hash; each file is at most 8 MiB and total inputs at most 16 MiB. The staged controller source and manifest are immutable hash bindings. This is a trusted-code route; an arbitrary supplied controller is executable code. Pin the reviewed controller hash in the caller. Do not reuse a previous request with changed source or inputs.

Operations are `inspect`, `prepare`, `submit`, `status`, `recover`, `collect`, `cancel`. After preparation, submit at most once; durable submission intent precedes process launch. Repeating submit only returns the existing attempt, including an uncertain attempt. A stale heartbeat reports `uncertain`; recovery is read-only and never relaunches or signals a stored PID. Cancellation writes a request for the owning controller. A prepared job may be cancelled before launch. Collection is terminal-only JSON containing explicitly named artifacts with base64 bytes and checksums, bounded logs, missing outputs and partial status. It does not write an arbitrary local collection destination. Callers must independently verify those records before writing files.

Windows drive-relative/UNC/device/ADS/reserved-name paths, case-fold collisions, file/directory collisions and reparse paths are rejected for job artifacts. Normal Unicode and spaces work as argument-array elements. The dedicated root and its ancestors must not be junctions or other reparse points. A trusted same-account process can still mutate files between checks; this worker does not defend against a hostile peer sharing its account.

## Process ownership and acceptance

The controller creates a kill-on-close Windows Job Object and a trusted Python gate. The gate cannot dispatch the command until assigned to that Job Object and explicitly released; assignment failure stops without dispatching the workload. Descendants inherit job membership. Cancellation, timeout, normal completion and controller loss close or terminate that owned tree. Only live process/job handles are used for termination. An owned process-tree cleanup failure remains uncertain and blocks collection. An inherited outer Job Object or site policy can reject assignment; this is a fail-closed runtime error, not evidence of successful cancellation.

From a checkout of the source repository, run `python evals/run_platform_acceptance.py windows` on actual Windows. This entry point requires all 11 worker-suite methods (7 native and 4 portable), rejects skips and records source/runtime provenance. The suite includes native subprocess lifecycle/restart, ambiguous attempt without duplicate dispatch, checksums/tamper, failure/bounds, cancellation/timeout grandchildren, controller death and junction rejection. Private independent review controls are prior evaluation evidence, not additional files the laptop must obtain. Running the underlying portable suite on another operating system does not close native acceptance.

Before claiming a Windows remote SSH route, additionally run the same lifecycle through an authorized Windows SSH endpoint, record authenticated host/user and host-key pins, source/manifest hashes, actual raw transport receipts, controller/client disconnect recovery and bounded collected bytes. Hosted Windows worker CI alone closes none of that transport gate.

Design basis: [Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects). Actual behavior must be verified on the selected Windows runtime.

Metadata readers and writers coordinate through a per-file Windows Global kernel mutex, identified by the actual TokenUser SID and normalized path. This covers cooperating processes across Windows sessions. Readers close their file handle before releasing the mutex; writers fsync temporary bytes before acquiring it and publish with atomic replacement. Acquisition and replacement retries share one one-second deadline. A denied or conflicting mutex fails closed, with no local-session fallback or persistent lockfile. After an abandoned mutex, an existing destination must still be bounded, regular, non-reparse JSON before publication; an established state file must still exist. Unrelated orphan temporary files are preserved.

Noncooperating handles can still deny replacement. Retries remain limited to native errors 5/32/33 and require regular files, no reparse/hardlink redirection and ownership matching the process TokenUser SID. The worker never changes permissions, deletes the destination or retries dispatch. Group-owned/elevated-token metadata may fail this strict predicate; mutex coordination does not override ownership. Native controls exercise held-reader serialization, deadlines, abandoned owners and unchanged bytes on refusal. This coordinates trusted same-account processes; it is not a security boundary against hostile peers or other accounts.
